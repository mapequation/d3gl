# d3gl — GPU-accelerated d3 rendering

**Date:** 2026-05-30
**Status:** Design approved, pending spec review

## Summary

d3gl is a TypeScript library that gives d3's drawing primitives a **polymorphic
rendering context** spanning SVG, Canvas2D, WebGL2, and (later) WebGPU. d3 already
went half-way: `d3-geo`, `d3-shape`, `d3-chord`, and `d3-hierarchy` don't draw — they
emit path commands (`moveTo`/`lineTo`/`bezierCurveTo`/`arc`/`closePath`) to a *context*.
Today that context is Canvas2D or an SVG path-string builder, and each requires
different rendering code. d3gl implements that same context interface across all
targets, so any context-driven d3 generator can render to the GPU **unchanged**.

The first consumer is geographic rendering for **Infomap Bioregions**: GeoJSON +
grid-cell maps with 10k–100k cells, colored by cell/bioregion properties via d3 color
scales, with pan/zoom and tooltips. The same engine then renders **phylogenetic trees**
(`d3-hierarchy`) — replacing `@phylocanvas/phylocanvas.gl` — and other chart types
(chord, arc, area) for free, because they all speak the same path language.

**GPU is the default interactive renderer; SVG/Canvas are produced on demand for
publication-quality export.** Performance on the live GPU view is the primary goal; when
trade-offs are unavoidable, performance wins over pixel-identical cross-target output.

## Motivation

The current bioregions renderer (v2, Canvas 2D) mutates the d3-geo projection
(`translate`/`scale`/`rotate`) on every zoom/pan event and re-runs `geoPath` over all
1k–100k cell polygons each frame — CPU bound. Phylogenetic trees are too slow to render
in full.

The usage profile is highly GPU-friendly: **geometry is near-static after the initial
load and bioregion computation; the live interactions are pan/zoom and recoloring**
(toggling bioregions ↔ heatmaps ↔ mixtures at bioregion or cell level, plus showing raw
point/range data). That maps directly onto *project & tessellate once → re-render with a
transform uniform and a color side-table*.

## Goals

- One d3-compatible drawing context interface, four backends (SVG, Canvas2D, WebGL2,
  WebGPU-ready via luma.gl).
- GPU-default interaction: pan/zoom and recolor are O(1) in draw calls and do not touch
  geometry.
- Support **any** d3-geo projection (project once on CPU; view transform on GPU).
- d3 color scales (sequential/continuous and categorical) with full fidelity — scales
  run on the CPU; results are uploaded as bytes.
- Tooltips via custom HTML/React overlay components.
- Publication export to SVG and PNG.
- Render whole phylogenetic trees on the GPU while keeping only visible labels in the
  DOM (the fix for the slow-tree problem).
- Headless, framework-agnostic core; thin optional React wrapper.

## Non-goals (v1)

- Pixel-identical output across targets (visually equivalent is the target; GPU is the
  fast interactive truth, SVG/PNG is publication output).
- A tiled basemap engine. MapLibre/raster basemaps are optional *interop* placed beneath
  the d3gl canvas, never part of the core.
- GPU MSDF text in v1 (reserved behind the LabelLayer API; HTML overlay ships first).
- Porting d3 color scales to GLSL (unnecessary — scales run on CPU at toggle time).

## Foundation decision

GPU backend is built on **luma.gl v9** (`Device`/`Buffer`/`Model`/shader/`RenderPipeline`
over WebGL2 + WebGPU).

Rationale, versus the evaluated alternatives:

- **From-scratch WebGL2** — rebuilds buffer/shader/program management and needs a manual
  WebGPU port later; luma.gl provides exactly this with WebGPU-readiness built in.
- **deck.gl** — wrong altitude: a declarative *layer* framework with a baked-in geo
  coordinate/projection model. Its headline feature (GPU projection) is the part we don't
  want, since we need arbitrary d3-geo projections. Interop at most, not a foundation.
- **react-map-gl / MapLibre** — tile basemap engine, Mercator-locked; cannot express
  arbitrary d3 projections or a general path context. Optional basemap layer only.
- **regl** — elegant but WebGL1/2 only, no WebGPU.
- **PixiJS v8** — a complete 2D renderer with `Graphics` + text. Rejected as foundation
  because: (1) it has **no SVG output** (SVG-in only), so the SVG backend must be built
  regardless — Pixi saves no SVG work; (2) its scene graph/text engine are bound to
  Pixi's own renderer and **cannot be grafted onto luma.gl** (they're an either/or for
  who owns the GPU); (3) its general scene graph fights the specific hot path (huge static
  geometry + frequent recolor) — changing a `Graphics` fill rebuilds geometry, and its
  batcher owns memory layout rather than us. The genuinely reusable pieces (earcut
  tessellation; MSDF atlas generators; `opentype.js`/`fontkit`) are standalone libraries
  usable directly with luma.gl.

The GPU-engine choice and the SVG-output choice are **orthogonal**: SVG comes from d3gl's
own SVG backend (built on the d3 context model) regardless of GPU engine.

## Architecture

### Layered structure

```
        d3 generators (geoPath, arc, line, link, ribbon…)
                         │  .moveTo/.lineTo/.bezierCurveTo/.arc/.closePath/.fill/.stroke
                         ▼
   ┌──────────────────────────────────────────────────────────┐
   │              Path Context interface (the seam)             │
   │  beginPath, moveTo, lineTo, quadraticCurveTo,              │
   │  bezierCurveTo, arc, rect, closePath,                      │
   │  fill(style), stroke(style), save/restore, setTransform    │
   └──────────────────────────────────────────────────────────┘
        │                 │                 │
        ▼                 ▼                 ▼
  ┌───────────┐    ┌────────────┐   ┌────────────────────────────┐
  │ SvgContext│    │CanvasContext│  │ GpuContext (retained)       │
  │ → <path>  │    │ → 2D ctx    │  │ record → tessellate → scene │
  │  strings  │    │ passthrough │  │ → luma.gl Models            │
  └───────────┘    └────────────┘   └────────────────────────────┘
        (export / publication)            (live interactive default)
```

The context interface matches the subset of `CanvasRenderingContext2D` that d3 calls, so
d3 generators drive any backend unchanged.

### Two execution modes behind one interface

- **Immediate** (SVG, Canvas2D): calls pass straight through to a path-string builder or
  the 2D context — equivalent to current d3 rendering. These are the export and fallback
  paths.
- **Retained** (GPU): calls are **recorded** into *drawables* (tessellated geometry + a
  style + a stable id). The scene holds drawables in GPU buffers and **replays** them each
  frame with only transform + color uniforms.

**Core design rule:** geometry production (tessellation) is separated from per-frame
rendering. The d3 generator is called **once** to build the scene; interaction never
re-invokes the generator.

### Drawable model

A *drawable* is one logical primitive (a grid cell, a tree branch, a chord ribbon),
addressed by a compact integer `drawableId` that is 1:1 with the caller's domain id
(`cellId`, `branchId`, …).

```
Drawable {
  id: number              // compact index; 1:1 with domain id; stable for picking/restyle
  fill:   { vertexRange, indexRange }    // earcut triangulation
  stroke: { vertexRange, indexRange }    // expanded stroke (joins/caps)
  style:  { fillColor, strokeColor, lineWidth, opacity }  // hot-swappable
  group:  string          // e.g. "cells", "land", "graticule", "branches"
}
```

### GPU buffer layout

All drawables in a group are packed into shared buffers (one draw call per group). Each
vertex carries its `drawableId`.

```
fill VBO     : [ x, y, drawableId ] × verts        // one big buffer, one draw call
fill IBO     : earcut triangle indices, per-drawable offset
stroke VBO   : [ x, y, drawableId, side ] × verts  // expanded ribbon geometry
colorTable   : [ r, g, b, a ] × MAX_drawables      // indexed by drawableId  ← hot-swap
flagsTable   : [ visible/selected/faded bits ] × MAX_drawables  ← hot-swap
```

Two keys for two jobs:

- **Per-vertex `drawableId`** drives **color** (the frequent case): recolor a primitive by
  writing `colorTable[drawableId]` — the GPU resolves which triangles automatically
  because they already carry the id. No triangle/range lookup needed.
- **Per-primitive buffer ranges** (`geometryIndex[id] → { fill, stroke } offsets/counts`)
  drive **geometry edits** (the rare case): overwrite the contiguous slice with
  `bufferSubData` — a single sub-upload, no full rebuild.

### The three hot paths (each O(1) in draw calls)

| Operation | What changes | Cost |
|---|---|---|
| Pan / zoom | `u_transform` (mat3) uniform | 1 uniform write, no CPU geometry |
| Recolor (toggle bioregion ↔ heatmap, restyle) | overwrite `colorTable`, or bind a precomputed alternate color buffer | 1 buffer upload, no re-tessellation |
| Show/hide group, select/fade | `flagsTable` or per-group uniform | 1 small upload |

The vertex shader applies the view transform; the fragment shader reads interpolated
color and the selected/faded flag (→ opacity). Because color is a vertex attribute fetched
via `drawableId`, the d3 color scale runs on the **CPU** at toggle time (cheap, 100k
lookups) and the GPU consumes the resulting bytes — full `d3-scale`/`d3-interpolate`
fidelity, no GLSL scale port.

**Precomputed color sets:** because toggling between bioregion / heatmap / mixture views
is the main interaction, d3gl precomputes one color buffer per view and switches by
binding a different buffer — instant, zero CPU at toggle time. Mixture blends are computed
once per parameter change.

### Stroke expansion

The GPU only draws triangles, so a stroke (a zero-area line) is expanded from
centerline + width into a ribbon of quads: **each straight segment → 1 quad → 2
triangles**, plus join triangles (miter/bevel) at corners. A stroked grid-cell border
≈ 8–12 triangles. A bioregion outline is the dissolved union boundary of a module's cells
(computed once), then stroke-expanded the same way.

### Anti-aliasing

WebGL2 MSAA framebuffer for fills; signed-distance edge AA in the fragment shader for
strokes so borders stay crisp at any zoom without re-tessellation.

### Tessellation off the main thread

earcut (polygon fill) + stroke expansion run in a **Web Worker** during streaming load,
producing transferable `ArrayBuffer`s appended to GPU buffers as they arrive. This
dovetails with the existing PapaParse chunk-streaming so the view fills in progressively
without main-thread jank and without a full rebuild per chunk.

### Curve flattening

Beziers/arcs are flattened to line segments before tessellation. Trade-off: flatten at
load tolerance and a curve can look faceted when zoomed in far. Grid cells have straight
edges (non-issue). Tree links, chord ribbons, and areas use curves — handled by a
sensible flattening tolerance, with optional re-flattening on large zoom steps.

## Maps specialization (@d3gl/geo)

### Project once

`geoPath` runs **once** at a fixed reference scale/translate using any d3-geo projection.
Output vertices are "reference projected coordinates" in GPU buffers. The live view
transform is a separate `mat3` applied in the shader.

```
load:      lon/lat ──d3.geoProjection──▶ reference px ──tessellate──▶ GPU buffers   (once)
interact:  reference px ──u_transform (mat3)──▶ screen   (every frame, GPU only)
```

Switching the d3 projection is a one-time reproject + re-tessellate (in a worker). Pan/zoom
never touches it.

### Zoom / pan

`d3-zoom` remains the input handler, but its `{k,x,y}` transform feeds the shader
`u_transform` uniform instead of mutating `projection.translate/scale`. Identical UX;
per-frame cost drops from "reproject 100k polygons" to "one uniform write."

### Globe rotation (orthographic) — the special case

A `mat3` cannot express sphere rotation, which changes geometry and visibility.

- **Zoom on the globe** = pure affine → shader transform (free, like flat maps).
- **Rotation (drag)** = two modes:
  - (a) **CPU reproject during the drag only**, reusing existing `versor` code (ships
    first; rotation is an occasional gesture, not steady state).
  - (b) **GPU orthographic vertex shader** taking lon/lat + a rotation quaternion uniform
    (opt-in fast path; rotation becomes free).

Backface culling drops far-hemisphere geometry via a normal-vs-view test (flag write or
shader discard).

### Streaming load

As cells are binned/finalized, the worker tessellates them and ships transferable buffers
appended to the GPU buffers progressively — map fills in while loading.

### Tooltips & hit-testing

Default keeps the existing CPU path: `projection.invert(mouse)` →
`quadtree.find(lon,lat)` → cell (with project-once, `invert` composes the inverse
reference projection with the inverse view transform). The hit primitive's centroid is
projected to screen to anchor a **custom HTML/React tooltip overlay**. GPU color-picking
(render `drawableId` to an offscreen target) is the fallback for primitives without a
spatial index (tree branches, ribbons).

### Raw-data layers

Point occurrences render as instanced quads/circles (one instance per point, cheap at
millions). Range maps from shapefiles are polygons tessellated like cells. Both are
additional drawable groups with their own show/hide flag.

## Trees and other primitives

The recolor/restyle and pan/zoom model is identical for all primitives; only the
tessellation step differs because each emits different path commands.

| Primitive | Generator emits | Tessellation (once) | Interaction |
|---|---|---|---|
| Grid cells / GeoJSON polygons | moveTo/lineTo/closePath | earcut → triangles | id→color swap |
| Phylo tree links | moveTo + bezierCurveTo (or right-angle lineTo) | flatten curves → stroke-expand | color/highlight clade = write descendant ids |
| Chord ribbons | moveTo/arc/bezierCurveTo | flatten → earcut fill | id→color swap |
| Arc/pie, area, line | arc/lineTo/bezier | flatten → fill or stroke | id→color swap |

Tree-specific concerns: curve-flattening tolerance for bezier links, and **GPU
color-picking** for hover (branches have no quadtree). A tree's structure is static after
layout, so highlighting a clade / coloring by trait / fading is just `branchId →
color/flag` writes. Layout recomputes only on re-root/collapse.

**Slow-tree fix:** all branches are GPU geometry; only visible, non-overlapping labels are
in the DOM (see Labels).

## Labels (@d3gl/labels)

`LabelLayer` is pluggable with three backends behind one API. The default fixes the
slow-tree problem (geometry on GPU, only readable labels in DOM).

| Backend | Sync | Scales to | Cost | When |
|---|---|---|---|---|
| **HTML/SVG overlay + viewport/collision culling** (default) | project anchors; throttle during zoom | ~hundreds visible | low | maps, readable trees |
| **Canvas-2D text layer** | shares `mat3` → auto-synced, zero per-label JS | low thousands | low-med | dense trees, no a11y |
| **GPU MSDF text** | text is geometry with the transform uniform → free, smooth | tens of thousands | high (atlas/glyph) | later, all-labels-always |

The HTML overlay's cost is DOM node count per frame, not sync correctness; culling keeps
it at a few hundred nodes. Canvas-2D and MSDF layers share the transform uniform, so they
have no per-label sync work.

## Public API

### Headless core

```ts
const renderer = createRenderer(parentEl, {
  target: 'webgl',          // 'webgl' | 'canvas' | 'svg'  ← the switch
  pixelRatio: devicePixelRatio,
});

const ctx = renderer.context;            // implements the Path Context interface
const path = d3.geoPath(projection, ctx);

renderer.scene.group('cells', (g) => {
  for (const cell of cells) {
    g.drawable(cell.id, (c) => path(cell.geometry));   // records + tessellates
  }
});

renderer.scene.style('cells', (cell, set) =>
  set({ fill: colorScale(cell.records), stroke: '#0003', lineWidth: 0.5 })
);

renderer.use(zoom());                    // d3-zoom → transform uniform
renderer.on('hover', (hit) => …);        // hit = { group, id }

const svg = renderer.toSVG();            // publication vector
const png = await renderer.toPNG({ scale: 3 });
```

The `target` option is the only thing that changes between GPU/Canvas/SVG; scene-building
and styling code is identical across all three.

### React wrapper

```tsx
<D3GL target="webgl" projection={d3.geoNaturalEarth1()} className="map">
  <Layer
    id="cells"
    data={cells}
    geometry={(c) => c.geometry}
    fill={(c) => colorScale(c.records)}     // recolor = cheap buffer write
    stroke="#0003"
    onHover={(cell) => setTooltip(cell)}
  />
  <Layer id="points" data={occurrences} geometry={pointGeom} visible={showRaw} />
  {tooltip && <Tooltip anchor={tooltip.screenXY}><CellCard cell={tooltip} /></Tooltip>}
</D3GL>
```

Tree variant uses the same shapes:

```tsx
<D3GL target="webgl">
  <Layer id="branches" data={branches} geometry={linkGeom}
         stroke={(n) => traitScale(n.trait)} onHover={setTipTooltip} />
  <Layer id="tips" data={leaves} geometry={tipGeom} fill="#333" />
  <LabelLayer data={visibleLeaves} text={(l) => l.name} anchor={tipAnchor} />
</D3GL>
```

Prop-change semantics:

- `fill`/`stroke`/`visible` → cheap `colorTable`/`flagsTable` writes (no re-tessellation).
- `data`/`geometry`/`projection` → re-tessellation (rare path).
- `target` → rebuild scene on the new backend.

**Design rule:** the React layer holds no rendering state — it diffs props and calls core
methods, keeping the core independently testable and usable without React. `useD3GL()`
returns the `renderer` for imperative control (custom animation, linked map↔tree views).

## Repo structure, build & testing

Monorepo (pnpm workspaces):

```
d3gl/
├─ packages/
│  ├─ core/          @d3gl/core   — Path Context interface, scene/drawable model,
│  │                                tessellation (earcut + stroke expansion), color/flag tables
│  ├─ backend-webgl/ @d3gl/webgl  — luma.gl Device/Model/shaders, buffers, picking, AA
│  ├─ backend-canvas/@d3gl/canvas — Canvas2D passthrough context
│  ├─ backend-svg/   @d3gl/svg    — SVG path-string context (export)
│  ├─ geo/           @d3gl/geo    — geoPath integration, project-once, d3-zoom→transform,
│  │                                versor globe, quadtree hit-test
│  ├─ labels/        @d3gl/labels — LabelLayer (HTML default; canvas/MSDF backends)
│  └─ react/         @d3gl/react  — <D3GL>, <Layer>, <Tooltip>, hooks
├─ examples/         — bioregions map, phylo tree, chord, "switch target" demo
└─ docs/
```

- `core` has zero GPU/DOM deps (pure geometry + scene logic; unit-tests in Node).
- Backends are swappable peers implementing the same context interface; `geo`, `labels`,
  `react` depend only on `core` interfaces, never on a specific backend.

**Build:** TypeScript; Vite library mode + `vite-plugin-dts`; ESM + CJS output; `d3`,
`react`, `@luma.gl/*` as peer deps.

**Testing:**

| Layer | Test type | Tool |
|---|---|---|
| `core` geometry (tessellation, ranges, color/flag tables) | unit, deterministic | Vitest (Node) |
| Context conformance (identical drawable graph from identical d3 calls, all backends) | unit | Vitest |
| WebGL backend | headless GL render → pixel snapshot | Vitest + headless-gl/Playwright |
| Cross-target parity (SVG/Canvas/WebGL within AA tolerance) | screenshot diff | Playwright |
| Performance budgets (recolor 100k cells, pan/zoom frame time, tessellation throughput) | benchmark + CI gate | Vitest bench |
| React (`<Layer>` prop diffs → correct core method: recolor vs re-tessellate) | unit | Testing Library |

Performance-budget tests are the safety net for the central thesis: CI fails if a recolor
stops being a single buffer write or pan/zoom regresses into re-tessellation.

## Key trade-offs (accepted)

1. **Immediate → retained.** The GPU backend records path calls into geometry buffers
   once, then replays with uniforms. This is the core engineering effort and the source
   of the performance win.
2. **Curve flattening vs zoom.** Faceting at extreme zoom for curved primitives; mitigated
   by tolerance and optional re-flattening. Non-issue for grid cells.
3. **Text.** HTML overlay first (not part of GPU output; culled to stay smooth);
   canvas-2D and GPU-MSDF backends reserved behind the LabelLayer API.
4. **Not pixel-identical across targets.** GPU AA/joins/text differ subtly from SVG/Canvas;
   "visually equivalent" is the goal, performance wins ties.
